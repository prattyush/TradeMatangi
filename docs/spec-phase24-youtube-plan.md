# Phase 24 follow-up: YouTube upload, saved links, desktop player

Status (2026-11-09): Y1 (#789), recording auto-stop (#790) and Y2 upload (#791) merged; Y3 saved links and videos in Analysis (#792) merged; Y4 local player optional, not started. Tool code stays on `dev` only. Builds on the Video Maker (see `spec-phase24-implementation-plan.md`).

## Decisions (user, 2026-11-09)
- **Permission:** upload only (`https://www.googleapis.com/auth/youtube.upload`). The app cannot edit, delete or list videos, and cannot set a thumbnail. Privacy/description changes are done in YouTube Studio.
- **Links:** kept on the server, tied to the trading session (so Analysis and other devices can show them).
- **Default visibility:** private.
- Playing: local mp4 in the desktop with clickable chapters. No YouTube embed (a private video will not play in an embed unless the window is signed in to YouTube); "Open on YouTube" opens the system browser.

## Design
- **Connect YouTube** button in the Video Maker. A second OAuth round (same loopback callback as login, PKCE, `access_type=offline`, `prompt=consent`) asking only for `youtube.upload`. The login flow is not changed. The YouTube refresh token is stored in the Windows Credential Manager under its own entry, never sent to the server.
- **Upload** in Rust (`reqwest`, resumable upload protocol): start session with `snippet` (title up to 100 characters, description up to 5000 bytes with no `<` or `>`, tags, category) and `status` (`privacyStatus`, `selfDeclaredMadeForKids=false`), then send the file in chunks with progress events and cancel. Resume after a dropped connection. Needs a confirmation step before upload (it publishes content outside the app).
- **Saved links:** new table (for example `VideoLinks`, key `session_id` + `video_id`) written through a small desktop endpoint under `/api/desktop/v1/` that checks the session belongs to the caller. Fields: `youtube_video_id`, `url`, `title`, `privacy`, `uploaded_at`, `chapters`. Not part of any trading path. Analysis can later show the link next to the session.
- **Player:** a `<video>` element on the local mp4 using Tauri's local-file support (`asset:` protocol scope for the chosen folder, and `media-src` in the CSP), with the chapter list as clickable seek points. Videos whose local file is gone show only the YouTube link.

## Y1 as built (connect)
- `windowsapp/src-tauri/src/youtube.rs`: second Google sign-in in the system browser (PKCE, loopback port 8765, same Google client and secret as the app login, fetched from the server's `google-config`), scope `youtube.upload` only, `access_type=offline`, `prompt=consent`. 3-minute wait for the browser, then a clear timeout message. Only the OAuth redirect counts (a stray `/favicon.ico` request is ignored). State is checked.
- The result is stored in Windows Credential Manager under its own target `TradeMatangi.Desktop.YouTube`: refresh token, current access token and expiry, and the client id/secret needed to refresh. Nothing goes to the server and the WebView never sees a token.
- If the consent screen is shown with the upload box unticked, the response lacks the scope and the app says so instead of saving a useless connection.
- `youtube_status` refreshes an expired access token. If Google answers `invalid_grant` (revoked, or the 7-day Testing expiry) the stored connection is deleted and the card says it ended. Offline keeps the connection. `youtube::access_token()` is what Y2 uses.
- `youtube_disconnect` asks Google to revoke the grant (best effort) and deletes the stored entry.
- UI: a "YouTube" card at the bottom of the Video Maker (`YoutubeConnect.tsx`): Connect / Disconnect and Google's error text (for example the Test users hint).
- A different Trade Matangi user on the same PC would share this YouTube connection (it is per Windows user, not per Trade Matangi account). Logging out of Trade Matangi does not disconnect it.
- Tests: 8 Rust unit tests (authorize URL, callback parsing, token response and scope check, refresh, freshness margin, error wording, storage format). The card was checked in a browser page with a mocked `invoke` (connect, waiting state, connected, disconnect, error). Not run against real Google.
- **Manual check (Windows build):** Video Maker > YouTube > Connect YouTube; the browser opens Google; pick the account/channel and tick the upload permission; the page says "connected"; the card shows "YouTube is connected". Close and reopen the app: still connected. Disconnect: back to Connect. Also try declining on Google's screen and confirm the message.

## Recording auto-stop (added 2026-11-09, dev only)
Stopping a trading session did not stop the screen recording, so the video kept recording dead footage. The recorder now stops 10 seconds after every session on screen has ended (see `docs/recording-metadata.md`, "Automatic stop"). Not on `preprod` yet.

## Y2 as built (upload)
- `windowsapp/src-tauri/src/youtube_upload.rs`: YouTube resumable upload with `reqwest::blocking` in `spawn_blocking`. One request starts a session (`snippet`: title, description, category 22; `status`: privacy, `selfDeclaredMadeForKids: false`); the file then goes in 8 MiB chunks with `Content-Range`. A dropped connection or a 5xx waits (2 s, 4 s, 8 s ...), asks the session how much it holds (`bytes */total`) and continues from there; 5 failures in a row end the upload with a clear message. The session address is the credential for chunks, so a long upload does not depend on the access token (the token is read once, at the start, through `youtube::access_token()`).
- Commands (`lib.rs`): `youtube_upload_start` (checks the request, returns a job id, progress through the `desktop-youtube-progress` event), `youtube_upload_cancel`, `youtube_open_video` (only a well-formed video id is opened, in the system browser), `pick_mp4_file`. One upload at a time (`UploadState`).
- Checks before sending: `.mp4`, not empty, title 1-100 characters, no `<`/`>` in title or description, description at most 5000 bytes, visibility private/unlisted/public. The same rules run in the UI (`uploadCannotStartReason`).
- Friendly messages for: daily quota (about 6 uploads a day), channel upload limit, no YouTube channel, refused permission, bad title/description, expired upload session, connection ended.
- If YouTube applies a different visibility than asked (it forces Private for API projects that have not passed YouTube's audit) the panel says so and points to YouTube Studio. The default visibility is Private.
- UI (`YoutubeConnect.tsx`, shown under the description once connected): the video (the one just made, or "Choose an mp4..."), title (default "SYMBOL DATE trades"), visibility, an explicit confirmation ("Upload x.mp4 to YouTube as Private?"), progress bar and Cancel, then the link with Copy and Open on YouTube.
- Tests: 13 Rust tests, 8 of them against a local fake YouTube server (chunking and `Content-Range`, resume after a dropped connection, 5xx retry and give-up, quota error, forced-private answer, cancel before and during, missing video id); 5 vitest cases for the model. The panel was checked in a browser page with a mocked backend (confirm, progress, cancel, done, open). **Not run against real YouTube.**
- Not in this step: saving the link on the server (Y3) and the player (Y4). Until Y3 the link is only shown in the panel after the upload: copy it.

## Y3 as built (saved links)
- **Table `VideoLinks`:** PK `session_id`, SK `video_id`; fields `user_id`, `title`, `privacy`, `chapters`, `uploaded_at`. Created lazily by `app/services/video_links_service.py` (like `BehaviorMarks`), so a server that never uses the tool never gets it. Also in `scripts/setup-dynamodb-tables.py`, `ddb_maintenance.SESSION_TABLES` (backup/restore/delete) and the session cascade delete (deleting a session deletes its links; the videos on YouTube are not touched).
- **The address is never stored from the client.** The client sends only the video id (11 characters of `A-Za-z0-9_-`); the server builds `https://www.youtube.com/watch?v=<id>`. Title 1-100 characters, visibility private/unlisted/public, chapter text at most 5000 bytes, at most 50 saved videos per session. Saving the same video again updates it and keeps its first upload time.
- **API `/api/video-links`:** `GET ?session_id=`, `POST`, `DELETE ?session_id=&video_id=` (router `app/routers/video_links.py`). **Owner only, reads included.** Analysis can share a real session read-only with other accounts, but a link can point at a private video, so a shared viewer gets 404. Reachable from the desktop as `/api/desktop/v1/analysis/video-links` (allowlisted in `desktop_analysis.py`, in the TypeScript and Rust path validators).
- **Desktop:** after an upload finishes, the YouTube card saves the link under each session selected for the video (the visibility YouTube actually applied is saved, so a forced Private is recorded as Private). If a save fails it says so and shows **Save link** to retry; the link is still on screen to copy. The new **Saved videos** card lists the links of all sessions in the open recording (grouped by video, newest first) with Copy link, Open on YouTube and Remove link (confirmed; removes only the saved link).
- A video chosen with "Choose an mp4..." while no recording is open has no session to attach to; the card says the link was not saved.
- **Videos in Analysis (website and desktop).** `shared/analysis/SessionVideos.tsx`, inside each expanded session in Analysis (above the Trades / Label Trades content), shows a collapsed "Videos (n)" row only for sessions that have a saved link (uploaded from the desktop). Expanded: title, visibility, date, **Open on YouTube**, Copy link and **Play here**. The host supplies `AnalysisEnvironment.videoLinks` (website: `getVideoLinks` + `window.open`; desktop: the `video-links` analysis route + `youtube_open_video`); without it, or with no links, or when the server answers 404 (a shared viewer of someone's real session), nothing is shown.
- **Embed on demand.** Play here loads `https://www.youtube-nocookie.com/embed/<id>` in an iframe only after the click (the id is checked first). The app cannot read a video's real visibility (upload-only permission), so the saved label can be out of date: a Private video shows a note to set it to Unlisted in YouTube Studio, and the link is always offered. Desktop CSP got `frame-src https://www.youtube-nocookie.com`. YouTube may refuse embeds in the desktop WebView (error 153); then the desktop falls back to Open on YouTube. **Not verified on Windows.**
- The local mp4 player with clickable chapters (old Y4) is optional and not part of this PR.
- **Tests:** 19 backend tests, also run against a real DynamoDB Local (lazy table creation, update in place, other user gets 404, session cascade delete) (`tests/test_video_links.py`: validation, update-in-place, cap, website and desktop owner checks, shared-read viewer refused, method allowlist, cascade delete with and without the table), `tests/test_ddb_maintenance.py` extended; Rust path-validator test; 15 vitest cases (`videoLinks.test.ts`, `sessionVideos.test.ts`). The cards were checked in a browser page with a mocked backend (auto-save, forced-private, failed save then retry, list, remove). **Not run on Windows or against the real server.**
- Not in this step: the local mp4 player (Y4, optional).

## Changing a video's visibility (question raised 2026-11-09, no code)
- **Not needed in the normal case.** The upload panel already lets you pick Unlisted when uploading, with only the `youtube.upload` permission. The embedded player works for Unlisted and Public videos.
- **What changing it later would need:** `videos.update` (50 units) with the `youtube` or `youtube.force-ssl` scope, both of which also allow editing and deleting all of the account's videos, plus a reconnect. The request must resend the whole `status` (omitted fields such as `embeddable` are cleared).
- **The real blocker is probably not the permission.** Google's `videos.insert` reference (the `developers.google.cn` copy, and secondary sources) says videos uploaded by an API project created after 2020-07-28 that has not passed YouTube's API audit are locked to Private, and that sending another `privacyStatus` does not lift it. The `.com` copy of the page, as summarised by the fetch tool, says the opposite, so this is not settled. A locked video is unlikely to be changeable through the API either. The first real upload shows which case applies: the app reports the visibility YouTube applied (`privacyNotice`).
- **Next step:** do one real upload on Windows with Unlisted selected. If YouTube keeps it Unlisted, nothing more is needed. If it forces Private and Studio also refuses Unlisted, the options are the audit, or uploading by hand in Studio and saving the link in the app (a small "Add a video link" feature, no extra permission).
- **Decision (user, 2026-11-09), superseded the same day:** first the plan was to switch a video to Unlisted by hand in Studio. The first Windows upload worked and switching to Unlisted in Studio worked, so the user then asked for the app to do it (section "Make Unlisted and Add a YouTube link" below).

## Fix: the YouTube connection was never kept (2026-11-09, first Windows run)
- **Symptom:** after approving on Google's screen the browser said "connected", but the Video Maker still showed Connect YouTube, with no error.
- **Cause:** `keyring = "3.6"` was built without its `windows-native` feature (the lock file had no Windows crates). Without it the crate uses a mock store that accepts a write but returns "no entry" to the next read, so the connection was thrown away. The browser page was also sent before the app had exchanged the code and saved anything.
- **Fix:** `windows-native` is enabled (the app's own sign-in, which uses the same crate, now also really lands in Windows Credential Manager, which is what its comments always said). `youtube.rs` now writes, reads back through a fresh entry and fails with a clear message if the value was not kept (unit test on the mock store). The browser page no longer claims success; it says Google answered and the desktop app reports the result.
- **Check on Windows:** Connect YouTube, then restart the app: it should still say connected. Also confirm the normal Trade Matangi sign-in is still remembered after a restart.

## Make Unlisted and Add a YouTube link (built 2026-11-09, after the first Windows upload)
- **Make Unlisted from the app.** Connect YouTube now asks for two permissions: `youtube.upload` (required) and `youtube.force-ssl` (optional; the user may leave it unticked on Google's granular consent screen, uploading then still works). The granted scopes are stored with the connection and `youtube_status` reports `canChangeVisibility`. A connection made before this change has no manage permission: Disconnect and Connect again.
- `youtube_set_visibility` (`windowsapp/src-tauri/src/youtube_visibility.rs`) reads the video's current `status` (`videos.list`, 1 unit) and sends it back through `videos.update` (50 units) with only `privacyStatus` changed. This matters: YouTube clears any `status` field a `videos.update` request leaves out (for example `embeddable`), so the short example found online would have switched embedding off. Read-only fields and `publishAt` are dropped. The answer's `privacyStatus` is what is reported and saved, so if YouTube keeps the video Private the app says so and the saved label stays Private.
- Where: **Make Unlisted** (with a confirmation) after an upload that ended Private, and on each non-Unlisted video in the Video Maker's Saved videos card. The label saved on the server for every session of the video is updated afterwards. Only Unlisted is offered in the UI (the Rust command also accepts private/public). **Public** is deliberately not offered: unaudited API projects may have it overridden (unverified), and public is a bigger step.
- Unverified until tried on Windows: whether YouTube accepts the change for a video its API project uploaded (a locked-Private video may refuse). The first real try decides.
- **Add a YouTube link** (website and desktop). `shared/analysis/AddVideoLink.tsx`: paste any YouTube address (watch, youtu.be, embed, shorts, live, or the bare id; anything else is refused), the title is read from YouTube's public oEmbed address (works from the browser: YouTube answers with CORS headers; a Private video cannot be read, then type the title), choose the label (default Unlisted) and Add link. Saved with the same `/api/video-links` call as an upload, under every session of the day. Where: the Videos row in Analysis on every expanded day the user owns (it now reads "Videos — add a link" when empty; sessions shared by someone else get no row), and the Video Maker's Saved videos card. **Remove link** (confirmed, saved link only) is also in the Analysis row.
- Quota wording: the "daily limit" message no longer says "about 6 uploads a day" (Google's current limit is 100 uploads a day).
- Tests: 8 Rust tests (`youtube_visibility.rs`: the update body keeps the settable status and drops the rest, request order and bearer token against a fake YouTube, permission/lock/not-found wording, input checks, applied-differs-from-asked) plus granted-scope parsing; vitest for URL parsing, the title lookup, and the visibility helper. The add-link form was checked in a browser page against a real oEmbed call (title of a public video read correctly).
